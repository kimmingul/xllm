# 모듈 분할 · 실행 귀속 설계

적대 리뷰: **codex@high × grok@high, 각 1라운드 (2026-08-23)**. 두 주제를 독립
프롬프트로 동시에 돌렸다. 코드 사실은 제안자가 직접 측정해 앵커했다.

## 주제 A — `xllm-advisor.js` 분할

### 측정

3,035줄 · export 70개. 다른 8개 모듈이 전부 이 파일에 의존하고, 이 파일은
`xllm-diff` 하나만 import 한다(순환 없음). 섹션: Public helpers 970 ·
CLI 422 · Run 415 · Artifacts 403 · Failure taxonomy 282 ·
Binary resolution 132 · Path discovery 121 · Process-discipline 77 ·
헤더(프로바이더 테이블·상수) 213.

### 제안자 원안이 수정됐다

원안은 "자기완결적인 5개 섹션 1,015줄을 1차 추출"이었다. 두 리뷰어가
독립적으로 같은 세 가지를 지적했다.

1. **상수/프로바이더 테이블 213줄을 빠뜨렸다.** 이걸 먼저 빼지 않으면 추출
   모듈이 상수를 얻으려 advisor를 역수입하고, 그 순간 facade와 leaf 사이에
   순환이 생긴다(ESM에서는 TDZ 오류로 나타난다). **모든 추출의 선행 조건.**
2. **Process-discipline(77)은 1차에서 빼면 안 된다.** spawn 수명주기·시그널·
   타임아웃과 결합돼 있어 독립 정책 객체가 아니다. Run과 함께 남긴다.
3. **Binary resolution과 Path discovery는 한 단위다.** PATH/PATHEXT/npm shim
   규칙을 나누면 경계만 늘어난다. 그리고 이건 전송층이라 CI가 검증하지 못하고,
   프로젝트 관례상 테스트만으로 출하할 수 없다.

또한 codex는 Artifacts(403)도 **순수 변환(cleaner)과 IO(저장)로 갈라야** 한다고
했고, Failure taxonomy는 **분류만** leaf로 보내고 재시도 실행 루프는 남기라고
했다.

### 줄 수는 근거가 아니다 (양쪽 합의)

> 소비자 8개가 70 export 한 점에 의존하는 구조는 facade를 남겨도 그대로다.
> 순이익의 근거는 **라이브 LLM 없이 새로 닫히는 실패 종류**여야 한다.

그 이득은 v0.33.0의 `spawnFn` 주입에서 이미 대부분 실현됐다. 판단 기준은
변경 동시성 · 의존 방향 · 테스트 격리 가능성 · 회귀 빈도이지 파일 크기가 아니다.

### 결정 — 1차는 두 개만

| 추출 | 근거 |
|------|------|
| `xllm-constants.js` | 모든 추출의 선행 조건. 부수효과 0, import 0 |
| `xllm-failures.js` | 순수 · 이미 단위 테스트 보유. 양쪽이 "좋은 첫 대상"으로 지목 |

**나머지는 전부 보류.** Public helpers 970줄이 진짜 순환 근원이며, 리뷰어들이
제시한 축(순수 파싱 / 프로필 읽기 / 정책 / 쓰기 / 위저드)으로 쪼개야 하지만
그 자체가 별도 설계 주제다. 전송층(binary/path/process-discipline)은 CI가
검증하지 못하므로 라이브 e2e 없이 옮기지 않는다.

### 중단 신호 (하나라도 나오면 1차를 되돌린다)

leaf가 facade를 역수입한다 · facade export 이름/개수가 달라진다 · 같은
stderr/exit에 taxonomy 픽스처가 다른 분류를 낸다 · 테스트가 모듈 몽키패치로만
통과한다 · process 핸들러가 중복 등록된다 · Windows npm shim 경로가 바뀌는데
CI는 통과한다 · 증거가 두 번 쓰이거나 격리 디렉터리 밖으로 나간다 ·
"상수만 조금만"이 세 번째 파일로 번진다.

## 주제 B — 실행 귀속

### 문제

`--multi` 인덱스 헤더가 **요청 스펙**을 라벨로 쓴다. 사용자가 `gemini:...`를
요청했지만 gemini CLI가 없어 실제로는 agy가 실행된 경우에도 인덱스는
`Providers: gemini:...`로 남는다.

### 코드로 확인한 사실 (리뷰어들이 요구한 증명)

인덱스만의 문제가 아니다. **원장이 요청 provider를 기록하고 traits가 그것을
읽는다.** `panel-ledger.jsonl`의 레코드는 `panelists[].{spec, provider}`를
담고, 패널은 자식 프로세스로 어드바이저를 띄우므로 이 값은 부모가 파싱한
요청 스펙이다. 즉 agy에서 실행된 결과가 `provider: "gemini"`로 집계된다.

### 판정 (양쪽 일치)

**해롭다.** 인덱스는 탐색·조인의 출발점이라 오귀속이 전파된다. 개별 아티팩트에
진실이 있는 것은 완화책이지 면죄가 아니다 — 기본 경로가 거짓이고 진실이 부가
경로에 묻힌 구조다.

**원장/traits 키는 해석된 실행 스펙이어야 한다.** 같은 agy 실행이 `gemini:X`와
`antigravity:X` 두 키로 갈라지면 표본이 분할·희석돼 라우팅 결정 자체가 틀린다.
요청을 잃는 위험은 UX/디버그 수준이고, 잘못된 키 집계는 의사결정을 틀린다.

**인덱스만 고치는 것으로는 불충분하다.** `runAdvisor`가 요청·해석·전송을
구조화해 반환하고, 인덱스와 원장이 **같은 반환값**을 소비해야 한다.

### 필드 계약

| 필드 | 의미 | traits 입력 |
|------|------|-------------|
| `requested_provider` / `requested_model` | 사용자가 요청한 것 | 아니오 (감사·UX 전용) |
| `executed_provider` / `transmitted_model` | 치환·교정 후 실제 실행 | **예 — 라우팅 키** |
| `substituted_from`, `model_correction_source` | 왜 달라졌는지 | 아니오 |

`transmitted_model`이 비면 기존 합의대로 **traits 입력에서 완전 제외**한다.
치환으로 실행 주체가 바뀐 경우 요청 벤더의 bare 키를 쓰지 않는다.

### append-only 호환

과거 레코드는 그대로 둔다. 신규 필드만 추가하고 **추정 마이그레이션하지
않는다**(파생 뷰 역기록 금지와 동일 원칙). 구 레코드는 키 결정 시 기존 규칙을
적용하고, 미확정이면 traits에서 제외한다.

### 최소한의 이름 정정

인덱스 헤더를 실행 기준으로 바꾸되, 요청을 보존하는 줄은 `Requested`로
명시한다 — codex 지적대로 `Providers`라는 이름 자체가 실행 주체로 읽힌다.
